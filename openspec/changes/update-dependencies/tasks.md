- [x] 3.4 Determined the highest `phpunit/phpunit` major compatible with this plugin's CI PHP baseline: `composer.json` declares no `require.php`, and `wordpress-plugin.yml` doesn't set an explicit PHP matrix, so the effective baseline is `holyhope/test-wordpress-plugin-github-action`'s default `php_version: '8.2'`. By PHP-version support alone, PHPUnit 13.x requires PHP >=8.4.1, 12.x requires >=8.3, and 11.x requires >=8.2 (compatible), with `yoast/phpunit-polyfills` 4.0.0 supporting `phpunit/phpunit ^11.0`. However, actually attempting the PHPUnit 11 bump (task 3.5) uncovered a *second*, PHP-version-independent constraint: PHPUnit 10+ dropped the legacy filename-based test discovery that this plugin's `wp scaffold plugin-tests`-generated `phpunit.xml`/test files depend on, which the PHP-support check alone did not surface. Net result: PHPUnit 9.x remains the actual highest compatible major for this plugin's current test tooling; see 3.5 for the fallback and its CVE-fix rationale.
- [x] 3.5 Attempted bumping `phpunit/phpunit` to `^11` (paired with `yoast/phpunit-polyfills` `^4`); local checks looked clean, but **CI revealed a real incompatibility**: PHPUnit 10+ removed the legacy filename→class discovery fallback that `wp scaffold plugin-tests`' generated `phpunit.xml` (`<directory prefix="test-" suffix=".php">`) and test files rely on — both our `tests/test-CFProjectDeploymentConfigEnvVarValue.php` and the CI-scaffolded `tests/test-sample.php` failed with "Class ... cannot be found" / "No tests executed!". Fixing this fully would mean restructuring the WP-CLI-scaffolded test tooling (out of scope for a dependency bump). **Fell back to `phpunit/phpunit ^9.6.33`** (latest 9.x, resolves to 9.6.36) per the fallback policy: this still fixes the original CVE-2026-24765 (patched as of 9.6.33) and keeps `composer audit` at zero advisories, while `yoast/phpunit-polyfills` stays on `^4` (supports both `^9.0` and `^11.0`). Documented in proposal follow-up notes (task 4.3).
